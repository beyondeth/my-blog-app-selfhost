# 🚀 글로벌 블로그 플랫폼을 위한 DB 최적화 완료

오늘 우리 블로그 플랫폼의 데이터베이스를 글로벌 서비스 수준으로 업그레이드하는 대규모 최적화 작업을 완료했습니다! 

## 📊 작업 배경

현재 블로그 플랫폼이 성장하면서 다음과 같은 과제에 직면했습니다:
- 사용자 증가로 인한 쿼리 속도 저하
- 글로벌 사용자를 위한 다국어 지원 부재
- 대용량 데이터 처리를 위한 확장성 부족

## 🔍 현재 DB 구조 분석 결과

### 데이터 규모
- **테이블 수**: 23개
- **총 데이터 크기**: 약 1MB (posts 테이블이 720KB로 72% 차지)
- **기존 인덱스**: 46개

### 발견된 문제점
1. **성능 병목**
   - 시간 기반 쿼리용 인덱스 부족
   - N+1 쿼리 문제 존재
   - 캐싱 전략 부재

2. **글로벌화 미지원**
   - 다국어 지원 구조 없음
   - 시간대 처리 미흡
   - 지역별 최적화 없음

3. **확장성 한계**
   - 파티셔닝/샤딩 미준비
   - 읽기 레플리카 미사용

## ✨ 개선 작업 내용

### 1. 인덱스 최적화 (즉시 적용)

20개의 핵심 인덱스를 추가하여 쿼리 성능을 대폭 개선했습니다:

```sql
-- 예시: 포스트 조회 최적화
CREATE INDEX idx_posts_published_at 
ON posts("publishedAt" DESC) 
WHERE "isPublished" = true;

CREATE INDEX idx_posts_blog_published 
ON posts("blogId", "isPublished", "publishedAt" DESC);
```

**추가된 주요 인덱스:**
- Posts: 발행일, 블로그별 조회, 커버링 인덱스
- Users: 로그인 시간, OAuth 제공자
- Notifications: 읽지 않은 알림 전용 인덱스
- Comments: 포스트별 댓글 정렬
- Files: 사용자별 파일 타입 필터

### 2. 글로벌화 지원 구조

12개 언어 지원을 위한 다국어 시스템을 구축했습니다:

```sql
-- 콘텐츠 번역 테이블
CREATE TABLE content_translations (
  entity_type VARCHAR(50),  -- 'post', 'blog', 'comment'
  entity_id UUID,
  language_code VARCHAR(10), -- 'ko', 'en', 'ja', 'zh'
  field_name VARCHAR(50),
  translated_value TEXT
);
```

**지원 언어 (12개):**
- 🇺🇸 영어 (English)
- 🇰🇷 한국어
- 🇯🇵 일본어 (日本語)
- 🇨🇳 중국어 간체 (简体中文)
- 🇹🇼 중국어 번체 (繁體中文)
- 🇪🇸 스페인어 (Español)
- 🇫🇷 프랑스어 (Français)
- 🇩🇪 독일어 (Deutsch)
- 🇵🇹 포르투갈어 (Português)
- 🇷🇺 러시아어 (Русский)
- 🇸🇦 아랍어 (العربية)
- 🇮🇳 힌디어 (हिन्दी)

### 3. 파티셔닝과 샤딩 이해하기

대용량 데이터 처리를 위한 두 가지 핵심 기술을 준비했습니다:

#### 파티셔닝 (Partitioning)
하나의 큰 테이블을 여러 작은 물리적 조각으로 나누는 기술입니다.

```sql
-- 예: notifications 테이블을 월별로 분할
CREATE TABLE notifications_2025_01 PARTITION OF notifications
  FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
```

**장점:**
- 필요한 파티션만 읽어서 쿼리 속도 향상
- 오래된 데이터를 파티션 단위로 쉽게 삭제
- 파티션별 병렬 처리 가능

#### 샤딩 (Sharding)
데이터베이스를 여러 물리적 서버로 분산하는 기술입니다.

```javascript
// 사용자 ID를 기준으로 4개 서버로 분산
function getShardId(userId) {
  return hash(userId) % 4;
}
// Shard 0: 250만 명
// Shard 1: 250만 명  
// Shard 2: 250만 명
// Shard 3: 250만 명
```

## 💡 기술적 인사이트

### 1. TypeORM 마이그레이션 팁
`CREATE INDEX CONCURRENTLY`는 트랜잭션 내에서 실행할 수 없습니다. TypeORM 마이그레이션에서는 `CONCURRENTLY` 키워드를 제거해야 합니다.

### 2. PostgreSQL 컬럼명 주의사항
TypeORM이 생성한 camelCase 컬럼명은 PostgreSQL에서 따옴표로 감싸야 합니다:
```sql
-- 잘못된 예
WHERE isPublished = true

-- 올바른 예  
WHERE "isPublished" = true
```

### 3. 커버링 인덱스의 위력
자주 조회되는 컬럼들을 INCLUDE 절에 포함시켜 인덱스만으로 쿼리를 처리:
```sql
CREATE INDEX idx_posts_list_covering 
ON posts("blogId", "isPublished", "publishedAt" DESC) 
INCLUDE (title, thumbnail, "viewCount", "likeCount");
```
