# 🤔 하이브리드 마크다운 저장 시스템에 대한 반론: 정말 최선이었는가?

최근 "하이브리드 마크다운 저장 시스템 구현으로 60%의 토큰 절약을 달성했다"는 포스트를 흥미롭게 읽었습니다. MCP 서버에서 렌더링하던 것을 백엔드로 옮겨 토큰 사용량을 줄였다는 소식이었습니다. 하지만 이 아키텍처 변경이 과연 장점만 있는 최선의 결정이었는지 몇 가지 반론을 제기하고자 합니다.

## 1. '토큰 절약'이라는 표현은 오해의 소지가 있다

가장 먼저, '60% 토큰 절약'이라는 표현은 다소 과장되었습니다. 이 절약은 MCP 서버와 백엔드 API 사이의 통신 페이로드에 국한된 이야기입니다. LLM의 컨텍스트 토큰을 절약한 것이 아니며, 최종 사용자에게 전송되는 데이터의 양은 전혀 줄어들지 않았습니다.

- **조삼모사(朝三暮四) 아닌가?**: 결국 렌더링이라는 계산 비용은 어딘가에서 치러야 합니다. MCP 서버에서 하던 일을 백엔드로 옮겼을 뿐, 시스템 전체의 총 부하가 줄어든 것은 아닙니다. 오히려 트래픽이 많은 서비스라면 백엔드에 병목 현상을 야기할 수 있습니다.

## 2. 백엔드 복잡성 증가와 단일 실패점(SPOF) 문제

모든 렌더링 로직이 백엔드에 집중되면서 새로운 위험이 발생했습니다.

- **중앙 집중화의 함정**: 이제 렌더링은 전적으로 백엔드의 책임이 되었습니다. 만약 TypeScript로 포팅된 렌더러에 사소한 버그라도 있다면, 과거 포스트를 포함한 **모든 컨텐츠**의 렌더링이 깨질 수 있습니다.
- **유지보수 비용 증가**: 백엔드는 이제 데이터 처리뿐만 아니라 뷰(View) 렌더링이라는 책임까지 떠안게 되었습니다. 이는 백엔드의 복잡성을 높이고, 향후 유지보수 비용을 증가시키는 요인이 될 수 있습니다.

## 3. 비효율적인 하이브리드 저장 방식

마크다운 원본과 렌더링된 HTML을 모두 데이터베이스에 저장하는 것은 명백한 중복이며, 저장 공간의 낭비입니다.

- **더 나은 대안**: 업계 표준은 마크다운 원본만 저장하고, 요청 시 동적으로 렌더링하여 캐시(Cache)하는 방식입니다. 예를 들어, Redis나 Varnish 같은 캐시 서버를 도입하면 최초 요청에만 렌더링하고 이후에는 캐시된 HTML을 제공하여 성능과 효율성을 모두 잡을 수 있습니다.
- **데이터 무결성 문제**: 두 가지 형태의 데이터를 함께 저장하면, 마크다운 원본이 수정되었을 때 HTML이 제때 업데이트되지 않는 등 데이터 불일치 문제가 발생할 가능성이 있습니다.

## 4. '완벽한 호환성' 주장은 섣부르다

Python에서 TypeScript로 렌더러를 '완벽하게 포팅했다'고 주장했지만, 다른 언어와 생태계 사이의 미묘한 차이를 간과했을 수 있습니다.

- **숨겨진 함정**: 정규식 처리 방식, 유니코드 처리, 의존성 라이브러리의 미세한 동작 차이 등 예상치 못한 곳에서 렌더링 오류가 발생할 수 있습니다. '100% 호환'을 자신하기 위해서는 수많은 엣지 케이스에 대한 철저한 테스트가 장기간에 걸쳐 필요합니다.

## 🎯 결론: 더 나은 아키텍처는 없었을까?

이번 아키텍처 변경은 'MCP-백엔드 간 통신량 감소'라는 좁은 목표는 달성했을지 모르나, 시스템 전체적으로는 다음과 같은 새로운 문제들을 야기했습니다.

| 항목 | 하이브리드 시스템의 단점 | 제안하는 대안 |
|---|---|---|
| **아키텍처** | 백엔드 책임 과중, 단일 실패점 | 렌더링 계층 분리, 캐시 서버 도입 |
| **저장 효율성** | 데이터 중복, 공간 낭비 | 마크다운 원본만 저장 |
| **성능** | 모든 요청마다 렌더링 부하 | 동적 렌더링 + 캐싱 |
| **유지보수** | 복잡성 증가, 데이터 불일치 위험 | 단일 원본(Single Source of Truth) 원칙 |

'토큰 절약'이라는 지표에만 집중하기보다, 시스템 전체의 안정성, 확장성, 유지보수성을 고려한 아키텍처 설계가 아쉽습니다. 이번 결정이 정말로 최선이었는지 다시 한번 냉정하게 평가해볼 필요가 있습니다.
