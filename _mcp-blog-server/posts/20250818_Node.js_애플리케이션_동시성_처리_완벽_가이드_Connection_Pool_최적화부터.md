## 동시성 문제의 발견

프로덕션 환경에서 다음과 같은 에러가 발생했습니다:

```
Error: timeout exceeded when trying to connect
```

50개의 동시 요청 중 단 8%만 성공하는 심각한 문제였습니다. 이는 Connection Pool이 고갈되어 발생한 문제였습니다.

## Connection Pool 이해하기

### Connection Pool이란?

데이터베이스 연결은 비용이 큰 작업입니다. 매번 새로운 연결을 생성하면:
- TCP 핸드셰이크 시간
- 인증 과정
- 세션 초기화

이를 해결하기 위해 **미리 연결을 생성해두고 재사용**하는 것이 Connection Pool입니다.

### Connection Pool 작동 원리

```
[Client Request] → [Pool Manager] → [Available Connection?]
                                           ↓ Yes     ↓ No
                                     [Use Connection] [Wait/Create New]
                                           ↓
                                     [Return to Pool]
```

### 주요 파라미터

| 파라미터 | 설명 | 기본값 | 권장값 |
|---------|------|--------|--------|
| max | 최대 연결 수 | 10 | CPU 코어 * 4 |
| min | 최소 연결 수 | 0 | max / 2 |
| connectionTimeoutMillis | 연결 대기 시간 | 0 | 10000 |
| idleTimeoutMillis | 유휴 연결 종료 시간 | 10000 | 30000 |

      ...baseConfig,
      url: dbUrl,
      ssl: { rejectUnauthorized: false },
      extra: {
        // Connection Pool 최적화

        query_timeout: parseInt(process.env.DB_QUERY_TIMEOUT || '30000', 10),
      },
    };
  }

  // 로컬 개발 설정
  return {
    ...baseConfig,
    host: process.env.DB_HOST || 'localhost',
    port: parseInt(process.env.DB_PORT || '5432'),

    password: process.env.DB_PASSWORD || 'postgres',

### 병목 지점 분석

1. **Connection Pool 고갈**
   - 50개 요청 > 20개 Pool = 대기 발생
   - 해결: Pool Size 증가

2. **트랜잭션 처리 시간**
   - 복잡한 JOIN 쿼리 = 긴 처리 시간
   - 해결: 쿼리 최적화, 원자적 연산

3. **Node.js Event Loop**
   - CPU 집약적 작업 = Event Loop 블로킹
   - 해결: Worker Threads, 비동기 처리

## 핵심 용어 설명

### Connection Pool
- **정의**: 데이터베이스 연결을 미리 생성하여 재사용하는 기법
- **장점**: 연결 생성 오버헤드 감소, 성능 향상
- **단점**: 메모리 사용량 증가, 설정 복잡도

### Connection Timeout
- **connectionTimeoutMillis**: 새 연결 생성 대기 시간
- **statement_timeout**: 단일 쿼리 실행 제한 시간
- **query_timeout**: 전체 쿼리 실행 제한 시간
- **idleTimeoutMillis**: 유휴 연결 유지 시간

### 동시성 (Concurrency)
- **정의**: 여러 작업이 동시에 진행되는 것처럼 보이는 것
- **Node.js**: 단일 스레드, 이벤트 루프 기반
- **처리 방식**: 비동기 I/O, 논블로킹

### 병렬성 (Parallelism)
- **정의**: 실제로 여러 작업이 동시에 실행
- **구현**: Worker Threads, Cluster Module
- **차이점**: 동시성은 논리적, 병렬성은 물리적

### Socket Hang Up
- **원인**: 서버가 연결을 갑자기 종료
- **발생 상황**: 타임아웃, 서버 과부하, 메모리 부족
- **해결**: Keep-Alive, 타임아웃 증가, 재시도 로직

// Connection Pool 모니터링
class PoolMonitor {
  private metrics = {
    totalConnections: 0,
    idleConnections: 0,
    waitingClients: 0,
  };

  async getPoolStats() {
    const pool = this.dataSource.driver.master;
    
    return {
      total: pool.totalCount,
      idle: pool.idleCount,
      waiting: pool.waitingCount,
      utilization: ((pool.totalCount - pool.idleCount) / pool.totalCount) * 100
    };
  }

  // 알림 설정
  checkPoolHealth() {
    const stats = this.getPoolStats();
    
    if (stats.utilization > 80) {
      this.logger.warn('Connection pool utilization high', stats);
    }
    
    if (stats.waiting > 10) {
      this.logger.error('Too many waiting clients', stats);
    }
  }
}

### 4. Circuit Breaker 패턴

```typescript
class CircuitBreaker {
  private failures = 0;
  private lastFailTime: Date;
  private state: 'CLOSED' | 'OPEN' | 'HALF_OPEN' = 'CLOSED';

  async execute(fn: Function) {
    if (this.state === 'OPEN') {
      if (Date.now() - this.lastFailTime.getTime() > 60000) {
        this.state = 'HALF_OPEN';
      } else {
        throw new Error('Circuit breaker is OPEN');
      }
    }

    try {
      const result = await fn();
      if (this.state === 'HALF_OPEN') {
        this.state = 'CLOSED';
        this.failures = 0;
      }
      return result;
    } catch (error) {
      this.failures++;
      this.lastFailTime = new Date();
      
      if (this.failures >= 5) {
        this.state = 'OPEN';
      }
      throw error;
    }
  }
}
```

## 추가 개선 사항

### 3. 캐싱 레이어 추가

## 마무리

동시성 처리는 단순히 Connection Pool 크기를 늘리는 것만으로 해결되지 않습니다. 
시스템 전체적인 관점에서:
- 적절한 Pool 크기 설정
- 쿼리 최적화
- 모니터링 구현
- 점진적 개선

이 네 가지를 균형있게 적용해야 안정적인 시스템을 구축할 수 있습니다.
